### 用户拒绝或纠偏的

**我推荐 Native 执行(一个会话依次实现 + 最后整体复核),用户选了 Subagent-driven(每 task 一个 subagent + 一个独立 reviewer)。**

我的推荐理由是:计划里已经把几乎每一步的完整代码和接口签名写死,subagent 拿到的信息不比我在同一会话里多,逐 task 换上下文主要是重复读同一份计划。用户没接受这个论证。

**这个分歧值得留着**——它说明用户对"中途独立复核"这件事的权重高于我对"上下文重复"的顾虑。后续章节排计划时,不要再默认推荐 Native。

### 翻车与返工

**1. 自查揪出一个会让 12 个 task 全部卡死的 bug**

Task 7 的 `api.py` 里写了 `from .service import extract_ticket, stream_chat`,但 `extract_ticket` 要到 Task 8 才被创建。**T7 自己就跑不起来,而且 T7 不过 T8 也做不了**——死锁。改成 T7 只 import `stream_chat`。

教训:写计划时按"最终状态"写 import,但执行是按 task 分步的,中间态的代码必须能独立 import。**逐 task 检查"这一步结束时代码能否运行"**。

**2. 计划里写了跑不通的测试代码**

- T6 原来直接 `monkeypatch.setattr(service.CHAT_PROMPT, "format_messages", spy)` —— `ChatPromptTemplate` 是 pydantic 模型,不允许随便挂新属性。改成整个替换为 `SpyPrompt` 包装类
- 并发断言 `assert [m.content for m in history[::2]] == ["问题一", "问题二"]` 依赖 `asyncio.gather` 的调度顺序;而后半段我一度写成恒真表达式。重写成**断言类型序列严格 human/ai 交替**——这才真正表达"两轮没交错写入"
- 漏了 `tests/__init__.py`,没有它 `from tests.sse_utils import ...` 和 `tests/eval/` 子包都 import 不了

**3. 写计划时发现 spec 本身的语义漏洞:退款 / 退货枚举重叠**

中文电商里"退货退款"通常是一个流程,`AfterSalesIntent` 里「退款」和「退货」模型很难只凭字面区分,会直接拉低评估准确率。

**处理方式**:不改 spec、不动枚举,把判定边界写死进 `EXTRACT_SYSTEM_PROMPT`(「退款」=只要钱不寄回,含退差价/退会员费;「退货」=要把商品寄回),评估集标注按这条边界写。**并预设了升级条件**:若评估显示两者互相错判 ≥3 条,说明枚举该合并,**停下来问用户,不自行改 schema**。

**4. 两处 API 靠 Context7 才写对**

- `GenericFakeChatModel` 的确切导入路径 `langchain_core.language_models.fake_chat_models`(不是 0.x 时代的 `langchain_core.language_models.fake`)
- `ChatOpenAI(streaming=True)` 本来打算写进工厂函数,查文档后**决定不写** —— 显式 `.astream()` 就会流式,少一个可能过时的参数

本阶段无用户介入,故无纠偏。但有一条**我替你做的决定**要留痕:

**`.env` 路径保持 CWD 相对,不改成指向包目录。** 评审把这条列为 Important,理由是磁盘上存在**两个** `.env`(worktree 一个、主仓库一个),从错误目录启动会静默指向另一份配置。我裁定的理由:spec 第六节只写"从 `.env` 读取",没规定解析规则;改成 `Path(__file__).resolve().parents[2]/'.env'` 会把目录结构写死进代码,非 editable 安装下反而更错。改用在 T9 的 dispatch 与 README 里写明"必须从仓库根启动"这条约定来消解。

**1. 预检扫描抓到 5 个计划缺陷,其中 1 个是实打实会挂的**

顺带确认 `trim_messages` 是**截到 human 边界**的(预算 30/35 返回 `[C,D]` 而不是 `[B,C,D]`),所以"不以 AI 开头"这条不变式在任何预算下都成立。裁定改成扫 9 个预算点、断言"非空时首条必为 HumanMessage" —— 比原断言更强,且实测可满足。

**教训**:写计划时"我觉得这个 API 会这样返回"就是赌。能在规划阶段跑一遍的,不要留到实现阶段才暴露。

**记一笔**:依赖约束写"不引 X"时,要连"传递依赖里有没有 X"一起想。

**3. 评审顺手验证了两处我担心"写成摆设"的断言**
