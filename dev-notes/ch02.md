### 我改了推荐的地方(自己推翻自己)

**上一轮我建议"未知 `conversation_id` 直接返回 404",这一轮我推翻了它。**

理由:那个建议是在**用自增 `id` 当身份**的前提下给的 —— 那时"存在但属于别人"的 id 挡不住,只能退而用 404 挡住"不存在"的那些。**加了 `session_id` 之后,这个补丁失去意义**:身份是 uuid4,猜不中存在的 id,而"带着一个我们没见过的 uuid"只有一种成因(本地存的历史已过期或库被重建),按它新建反而让客户端能自救。

### 翻车与返工

**1. 用户说"表语句在 C:\Users\27497\projects\sql",实测 `sql.txt` 是 0 字节**

`ls -la` 看大小 0,`find` 也没找到别的 `.sql` / DDL 文件。**如实报告文件为空并请用户粘贴,没有猜内容**。

这是本项目**第三次**同一形状:ch01 两次"`.env` 说填好了但没填",这次是"表语句在那个路径但文件是空的"。**原则已固化:用户自述的状态一律先用命令复核。**

**2. 中文 ENUM 存的是成员名不是值 —— 第二类坑**

实测:`Enum(ConvStatus)` 不写 `values_callable` 的话,库里落的是 `ConversationStatus.ongoing` 而不是 `进行中`。

与 ch01 撞过的 `f"{intent}"` 得到 `AfterSalesIntent.refund` **是同一类坑**:

```python
Enum(ConvStatus, values_callable=lambda e: [m.value for m in e])
server_default=text("'进行中'")     # SQL 字面量要自带引号
```

改完实测:MySQL 侧产出 `ENUM('进行中','已转人工','已结束') NOT NULL DEFAULT '进行中'` —— **与你 DDL 逐字一致**;SQLite 落库原值 `进行中`。

**3. `BIGINT` 主键在 SQLite 上不自增 —— 第三类坑**

SQLite 只把**类型名恰好为 `INTEGER`** 的列当 rowid 别名。`BIGINT` 拿不到自增,测试插两行会撞主键。

```python
mysql.BIGINT(unsigned=True).with_variant(Integer, "sqlite")
```

实测:MySQL 侧 `BIGINT UNSIGNED`,SQLite 侧两次插入拿到 `id = 1, 2`。

**4. `ON UPDATE CURRENT_TIMESTAMP` 是 ORM 产不出来的 —— 这条直接改了架构决策**

本来打算"模型是唯一真相,`create_all` 建表,`.sql` 只当文档"。实测下来 ORM 能复刻的比预想的多:

| 你的 DDL 要素 | ORM |
|---|---|
| `BIGINT UNSIGNED` | ✅ |
| `ENUM(...) DEFAULT '进行中'`(中文值) | ✅ 逐字 |
| `DEFAULT CURRENT_TIMESTAMP` | ✅ |
| `CONSTRAINT fk_... FOREIGN KEY(...)` | ✅ |
| `ENGINE=InnoDB CHARSET=utf8mb4 COMMENT='...'` | ✅ |
| `KEY idx_user_id (user_id)` | ⚠️ 能建,但不内联进 `CREATE TABLE` |
| **`ON UPDATE CURRENT_TIMESTAMP`** | ❌ **`server_onupdate` 不落 DDL** |

最后一行是关键:让 `create_all` 建 MySQL 表,`updated_at` 就**永远不会自动更新** —— 而那是用户写进 DDL 的东西。所以**分工改成**:MySQL 由 `sql/ch02-ddl.sql` 建(权威),SQLite 由 `create_all` 建(测试),两者的漂移由 `test_db_ddl_drift.py` 守住。

**又一次"本机跑一遍改变了设计"** —— 这次改变的是一个架构级的决策,而不是一个参数。

**5. 控制台编码**

默认 GBK 控制台会把中文输出打成乱码,探针脚本得加 `PYTHONIOENCODING=utf-8 PYTHONUTF8=1`。已记,后续所有带中文断言的脚本一律加。

### 这一段最值钱的四个发现

计划的代码是逐字抄下来的,但**四处抄下来就是跑不通** —— 而且每一处的失败都指向一个真实的认知缺口,不是笔误:

**1. `SessionFactory = type(SessionLocal)` 取到的是类,不是实例(纯运行时缺陷)**

`type(SessionLocal)` 是 `sessionmaker` **这个类**。`SessionFactory()` 于是造出**另一个没绑 engine 的 sessionmaker**,不是 Session。下游 20 处一律 `with session_factory() as session` —— 全都会炸在 `UnboundExecutionError`。静态看毫无异样,是我那条**改写过的**测试(`test_session_factory_produces_sessions_without_connecting`)第一次真的调它才炸出来。

**这条值得记的原因**:计划里原本那条测试是 `assert issubclass(Session, Session)` —— 恒真式,什么也钉不住。**一个不承重的测试,会把一个承重的缺陷放过去。**

**2. SQLite 的索引名是库内唯一,MySQL 是表内唯一**

权威 DDL 里 `messages` 与 `tickets` 都有 `KEY idx_conversation_id` —— MySQL 合法,SQLite 第二条 `CREATE INDEX` 直接撞名。处置是给 `tickets` 那条加 `.ddl_if(dialect="mysql")`,实测三件事都对:SQLite 建表跳过它、MySQL 方言编译输出不变、`table.indexes` 里两个对象都还在(漂移测试照样断言得到)。

**3. `Enum.create_constraint` 自 SQLAlchemy 1.4 起默认 False**

计划里有一条测试断言「ENUM 在 SQLite 上落成 CHECK 并真的拒非法值」,而实测 SQLite 侧只有一列裸 `VARCHAR`,`role="system"` 照收不误。查 spec §17 —— **spec 把这条列为交付项**。所以是实现缺口,不是测试写错:补 `create_constraint=True`。实测 MySQL 侧编译输出**一字未变**(原生 ENUM 已承担约束,SQLAlchemy 不再叠 CHECK),不影响漂移测试。

**4. `.venv` 里的 editable 安装指向的是 ch01-conversation/src**

`direct_url.json` 写着 `file:///.../ch01-conversation`。也就是说:**从 ch02 开工到现在,每一条测试都在导入 ch01 的源码**,新建的 `mewhelp.db` 根本不可见。是 T2 第一条测试报 `No module named 'mewhelp.db'` 才暴露的(不是"db 写错了",是"根本没在看这个目录")。

### 这一段最值钱的四个发现

**1. LIKE 的转义不是"防御性编程",是载荷性的**

`query_faq` 的关键词来自模型。计划里要求转义 `%` 与 `_`。我在 3 条 FAQ 的库上实测了对照:

| keyword | 转义后 | 去掉转义 |
|---|---|---|
| `%` | 0 条 | **3 条(全表)** |
| `_` | 0 条 | **3 条(全表)** |

也就是说不转义时,模型抽出一个 `%` 就能拿到全表政策去编答案,而**没有任何报错**。`_` 更隐蔽 —— 它匹配任意单字符,几乎每行都中。测试因此不是恒真式。

### 那条 Important:前端徽章按工具名配对,配错了

一轮里**同一个工具可以被调两次**(现实问法:「订单 1001 和 1002 的物流到哪了」),
而页面把徽章按工具名存成单个节点。第二个 start 覆盖第一个,第二个 end 落空。

实测出来的后果比"徽章转圈不停"更难看:**第二个徽章拿的是第一个调用的耗时** ——
harness 打出来是 `"🔧 查物流" | "🔧 查物流✓ 3 ms"`,而两个调用分别是 3.4 ms 与 5.1 ms。
**徽章照样收尾、照样有 ms,是一份看起来正常的错数据。** 这比转圈不停更坏,
因为没有人会去查一个"看起来对"的数字。

改成按名字排队、先进先出;同时把前端依赖的那条顺序不变量(`start` 与 `end` 一一对应)
钉在**服务端**的用例里 —— 否则前端就在暗中依赖另一个模块的发射顺序。
