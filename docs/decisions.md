### 决策:Ch01 会话状态放进程内存,而不是 MySQL

- **选了什么**:进程内 `SessionStore`(dict + per-session `asyncio.Lock`),接口做成 async 以便后续替换
- **为什么**:本章的目标是跑通"裁剪 + token 预算"这个机制,不是把存储做对。起 MySQL 要建表、要 docker compose,会把体重从对话本身拉偏
- **考虑过的替代方案**:
  1. MySQL 持久化 —— 架构图数据层本来就有,但对第 1 章太重
  2. 完全无状态,历史由客户端每次全量带上 —— 最省事,生产也常见,但验收②用 curl 演示要手贴全部历史,"多轮上下文管理"在代码里几乎没有落点
- **代价 / 风险**:进程重启会话即丢;多 worker 不共享;内存无上限、无淘汰。换持久化只需替换 `SessionStore` 一个类

### 决策:失败的那一轮不写进会话历史

- **选了什么**:一轮对话只有在**模型完整答完**之后才 `append` 进历史;中途上游报错、或模型返回空内容,这一轮的 human + ai **一对都不写**。已推出的 token 照常推给客户端,然后补一个 `error` 事件收尾
- **为什么**:三件事同时成立才选它 ——
  1. **重试是完备的**:客户端手里本来就握着自己刚发的那句话,"把同一条消息原样再发一次"就够了,不需要补发任何更早的对话
  2. **不污染历史**:如果把这轮写回去,半截的回答会留在这个会话里,此后**每一轮**都带着它
  3. **不静默失败**:空回复如果当成成功写回,客户端会收到一个零 token 的 `done`,这是最坏的一种——看起来一切正常
- **考虑过的替代方案**:
  1. 写回半截回答 —— 上下文里留一条断掉的 ai 消息
  2. 写回用户提问、丢掉回答 —— 下一轮模型会看到两条连续的 human,且重试时会重复计一轮
  3. 报错即销毁整个会话 —— 用户为了一个网络抖动丢掉全部上下文,惩罚过重
- **代价 / 风险**:客户端**必须**知道"重发同一条消息"这个契约,否则可能换一个 `session_id` 重发,那才会真的丢上下文。所以这条写进了 `api.py` 的模块 docstring —— 它是对外契约,不是内部实现细节

## 关键决策(Ch02)

### 决策:"只做单轮"靠**收敛那步不绑工具**来保证,不靠 Prompt 嘱咐

- **选了什么**:turn1 用 `model.bind_tools(5 个).astream(messages)`;拿到 `tool_calls` 后执行工具,再起 turn2 —— **turn2 是 `model.astream(messages)`,不调 `bind_tools`**。模型在收敛那一步手里根本没有工具的定义,想调也调不出来。
- **为什么**:用 Prompt 写"你只能调一次工具"是在**请求**模型守规矩;不绑工具是在**结构上**让它无从违反。前者会随模型版本、上下文长度、措辞漂移,后者不会。本章的验收标准是可复现的,不该建立在一个概率性的自我约束上。
- **考虑过的替代方案**:
  1. Prompt 里写死"只调用一次工具" —— 最省事,但把正确性押在模型的服从性上;换个模型就可能变成多轮,而**多轮 Agent Loop 是本章明确不做的**
  2. 检测到 turn2 又产出 `tool_calls` 就报错 —— 能兜住,但那是在**运行期**才发现违规,而且要给用户看一个错误
  3. 用 `max_iterations` 之类的循环上限 —— 那是给多轮 Agent 用的护栏,本章没有循环
- **代价 / 风险**:turn2 无法再查任何东西。用户在一轮里问了两件事(比如"订单 1001 到哪了,顺便告诉我降噪耳机多少钱"),turn1 的 `tool_calls` 里会同时带上两个工具调用 —— 这是允许的(`run_all` 并发执行),但如果模型在**收敛**时才发现还需要查第三个,它只能如实说查不了。这是单轮设计的固有代价,写进了 spec

### 决策:上下文源从内存 `SessionStore` 改为**按 `conversation_id` 从 DB 回放**

- **选了什么**:每轮开始时按 `conversation_id` 读 `messages` 表,经**回放过滤**后组装成上下文。
- **为什么**:加了 `conversations.session_id` 之后,DB 回放变成干净的选项,而且**顺手消掉了「内存 store 与 MySQL 两个真相」那道缝** —— 否则会话历史在内存里、消息流水在库里,两边迟早对不上,而"以哪边为准"会变成一个每次都要重新回答的问题。
- **回放过滤**:只回放 `role=user`,以及「`role=assistant` 且 `content` 非空且 `tool_calls` 为空」的消息 —— 也就是每轮的提问与最终回答。带 `tool_calls` 的 assistant(常夹带 preamble)与 `tool` 消息**不跨轮回放**,避免续接时模型看到自己上一轮的半截前言。**但全部消息仍完整落库**,备追溯。
- **考虑过的替代方案**:
  1. 沿用 ch01 的 `SessionStore` 当上下文源 —— 用户一开始选过;代价是进程重启即丢,且两个真相
  2. 全量回放(把 `tool_calls` 与 `tool` 消息也带进上下文)—— 更"完整",但会把上一轮的工具往返重新喂给模型,既费 token 又可能诱导它模仿着再调一次
- **代价 / 风险**:每轮多一次 DB 查询。消息多了以后需要分页/截断策略 —— 本章的 `trim_history` 仍然兜底,但没有按 `conversation_id` 做增量读

### 决策:`conversations.session_id` 是本章**唯一**一处偏离课程原始 DDL 的列

- **选了什么**:加一列 `session_id VARCHAR(64) NOT NULL UNIQUE`,用途只有一个 —— **聊天页手上那个不透明 session_id → 会话行的映射**。
- **为什么**:用自增 `id` 当会话身份是**可枚举**的,猜中即读到别人的会话。`session_id` 用 uuid4,不可猜。
- **考虑过的替代方案**:
  1. 直接用自增 `id` 当身份 —— 少一列,但把"猜 id 读别人的会话"变成一个 GET 就能试的事
  2. 加一张 `session_map` 关联表 —— 更"规范化",但为了一列映射多一张表,不划算
- **代价 / 风险**:`sql/ch02-ddl.sql` 与课程原始 DDL 不逐字一致。`test_db_ddl_drift.py` 因此**以本 spec 为准**,而不是以原始 DDL 为准 —— 这条偏离用户已批准,并写进了 spec §6.3 与 §17 的偏离清单

### 决策:`sql/ch02-ddl.sql` 当权威,而不是 SQLAlchemy 的 `create_all`

- **选了什么**:建表以手写的 `sql/ch02-ddl.sql` 为准;ORM 模型只做读写映射,不负责产 DDL。
- **为什么**:实测 ORM 的 `server_onupdate` **产不出 `ON UPDATE CURRENT_TIMESTAMP`**。用 `create_all` 建出来的表,`updated_at` 不会自动更新 —— 而这件事在应用层完全看不出来(它只会"看起来一直没更新过")。手写 DDL 能如实表达。
- **考虑过的替代方案**:
  1. `create_all` —— 少维护一份 DDL,但要么丢掉 `ON UPDATE CURRENT_TIMESTAMP`,要么在 Python 侧手动赋值(那就变成"每处写入都得记得",迟早漏)
  2. Alembic 迁移 —— 生产上是对的,但本章只有四张表、还没有历史包袱,引入迁移框架是给第 3 章之后准备的
- **代价 / 风险**:DDL 与 ORM 模型可能漂移。`test_db_ddl_drift.py` 就是钉这件事的:它比对 DDL 与模型,任何一边改了另一边没跟上就红

### 决策:mock 数据由**入参**定种子,让验收①可复现

- **选了什么**:`query_order` / `query_logistics` / `query_product` 三个工具不连任何外部 API,用入参(订单号/商品名)哈希出稳定的伪随机数据。
- **为什么**:验收①要断言"答案是**基于工具返回的数据**得出的"。如果每次调用返回的物流节点都不一样,就没法判断模型是在读工具结果还是在编 —— **可复现是这条验收能成立的前提**。
- **考虑过的替代方案**:
  1. 每次调用真随机 —— 更像"真实环境",但验收①失去判据:模型说什么都可能是对的
  2. 固定一份写死的数据表 —— 可复现,但"订单 1001"和"订单 9999"返回同一条,一问就穿帮
- **代价 / 风险**:同一个订单号永远返回同一个结果,多跑几次会看出来是造的数据。这是演示项目的有意取舍,不是要上生产

### 决策:写类工具(`create_ticket`)**一律不重试**

- **选了什么**:`execute_tool` 对超时与瞬时异常重试 3 次;但 `create_ticket` 这类写操作**任何情况下都不重试**。
- **为什么**:没有幂等设施,超时重试会**重复建单** —— 用户投诉一次,工单出来两张。这条与"参数错不重试"是**独立的两个判断**:即使成因确实是瞬时异常,写操作也不重试。
- **考虑过的替代方案**:
  1. 给 `create_ticket` 加幂等键,然后照常重试 —— 这是生产上的正解,但本章没有幂等设施,加一个只为一个工具服务的设计不划算
  2. 靠 `ticket_no` 撞主键挡住重复 —— `ticket_no` 是入参生成的,重试时**还是同一个号**,确实会撞主键;但那是"碰巧挡住",不是设计。`ticket_no` 撞主键后的**递增重试**是另一回事(工具内部换一个号再试,不是盲目重放)
- **代价 / 风险**:`create_ticket` 遇到瞬时故障时直接失败,不重试。用户看到的是"建单失败",需要重发

### 决策:落库失败**只记日志**,不补 `error` 帧

- **选了什么**:一轮答完之后写 `messages` 失败,只写日志,已经推给用户的 token 与 `done` 帧不动。
- **为什么**:token 已经逐字吐给用户了,这时候因为落库失败补一个 `error` 帧,**是在骗人** —— 用户明明看到了完整回答,却被告知这一轮失败了。而且客户端契约是"看到 `error` 就重发同一条消息",于是用户会重发,又答一遍、又落库失败,变成一个循环。
- **考虑过的替代方案**:
  1. 补 `error` 帧 —— 上面说的骗人与循环
  2. 整个请求返回 500 —— 更糟,响应头早就发出去了
  3. 丢掉这一轮不落库、静默继续 —— 就是选了的这个;区别只在于**要记日志**
- **代价 / 风险**:落库失败对用户不可见,只能靠日志发现。代价是"用户以为聊过、下一轮发现它忘了"——承认这一点,比撒谎好

### 决策:工具的上下文注入用**闭包**,不用 `InjectedToolArg`

- **选了什么**:`query_faq` / `create_ticket` 需要 DB 会话,做法是 `build_registry(session_factory)` 用**闭包**把工厂包进工具函数。
- **为什么**:`InjectedToolArg` 在 langchain-core 1.6.5 上**实测静默失效** —— 标注了它的参数照样出现在 `convert_to_openai_tool()` 的 `required` 里,于是模型被要求提供 `session_factory` 这个它根本给不出的东西。**静默**是关键:它不报错,只是让工具从此不可用。
- **考虑过的替代方案**:
  1. `InjectedToolArg` —— 框架提供的正解,但在这个版本上不工作(见 NOTES.md)
  2. 用全局/模块级 Session —— 工具跑在线程池里,`Session` 非线程安全,跨线程共用会炸得莫名其妙
- **代价 / 风险**:工具与工厂耦合在构造期,`build_registry` 因此必须带参数。测试里每个用例都要自己造一个工厂 —— 这反而是好事,它让"工具用的是哪个库"变得显式

### 决策:中文 ENUM 必须带 `values_callable`

- **选了什么**:`status` / `role` / `ticket_type` 这些值是中文的枚举列,ORM 侧一律用 `values_callable` 指定"存进库的是**值**不是成员名"。
- **为什么**:SQLAlchemy 的 `Enum` **默认存成员名**。不指 `values_callable`,`'进行中'` 会被存成 `PENDING` 之类,与 `sql/ch02-ddl.sql` 里的中文 ENUM 定义对不上 —— 而症状是 `Data truncated for column` 或者干脆写不进去,报错信息指不到"枚举存的是名字"这件事上。
- **考虑过的替代方案**:
  1. 改用英文枚举值 —— 逃开这个问题,但 `faq` 表的中文分类是给演示看的,数据库里全是拼音/英文反而更难核对
  2. 不用 `ENUM`,用 `VARCHAR` + 应用层校验 —— 丢掉数据库层的约束,本章的 DDL 显式要求 ENUM
- **代价 / 风险**:每个中文枚举列都得记得加 `values_callable`,漏一个就是运行期才发现。`test_db_ddl_drift.py` 会在 DDL 与模型之间比对,能挡住这类漂移

### 决策:不用异步 SQLAlchemy

- **选了什么**:同步引擎 (`pymysql`) + `sessionmaker`,工具函数是同步的,由 `@tool` 的 `ainvoke` 丢进线程池。
- **为什么**:**实测要 +3 个依赖**(greenlet / asyncmy / aiosqlite 全缺),换来的是本章不需要的并发。工具的阻塞由 langchain 代劳 —— 它对同步函数的 `ainvoke` 已经把调用丢进线程池(实测跑在 `asyncio_0` 线程)。
- **考虑过的替代方案**:
  1. `asyncmy` + `AsyncSession` —— 生产上是对的,但本章的并发量是"一个人在一个浏览器里点四条",异步带来的吞吐完全用不上
  2. `aiosqlite` 只给测试用 —— 测试确实用它,但那是测试侧的事,不影响主链
- **代价 / 风险**:工具跑在线程池里 → **`Session` 不能跨线程共用**。这就是编排层收的是"能开新 Session 的工厂"而不是一个 `Session` 的原因(见 `ch02/api.py` 的 `get_session_factory` 与 spec §9.2)。往后的工具函数必须遵守这条,否则会得到难以定位的跨线程错误
