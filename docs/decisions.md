### 决策:Ch01 会话状态放进程内存,而不是 MySQL

- **选了什么**:进程内 `SessionStore`(dict + per-session `asyncio.Lock`),接口做成 async 以便后续替换
- **为什么**:本章的目标是跑通"裁剪 + token 预算"这个机制,不是把存储做对。起 MySQL 要建表、要 docker compose,会把体重从对话本身拉偏
- **考虑过的替代方案**:
  1. MySQL 持久化 —— 架构图数据层本来就有,但对第 1 章太重
  2. 完全无状态,历史由客户端每次全量带上 —— 最省事,生产也常见,但验收②用 curl 演示要手贴全部历史,"多轮上下文管理"在代码里几乎没有落点
- **代价 / 风险**:进程重启会话即丢;多 worker 不共享;内存无上限、无淘汰。换持久化只需替换 `SessionStore` 一个类

### 决策:失败的那一轮不写进会话历史

- **选了什么**:一轮对话只有在**模型完整答完**之后才 `append` 进历史;中途上游报错、或模型返回空内容,这一轮的 human + ai **一对都不写**。已推出的 token 照常推给客户端,然后补一个 `error` 事件收尾
- **为什么**:三件事同时成立才选它 ——
  1. **重试是完备的**:客户端手里本来就握着自己刚发的那句话,"把同一条消息原样再发一次"就够了,不需要补发任何更早的对话
  2. **不污染历史**:如果把这轮写回去,半截的回答会留在这个会话里,此后**每一轮**都带着它
  3. **不静默失败**:空回复如果当成成功写回,客户端会收到一个零 token 的 `done`,这是最坏的一种——看起来一切正常
- **考虑过的替代方案**:
  1. 写回半截回答 —— 上下文里留一条断掉的 ai 消息
  2. 写回用户提问、丢掉回答 —— 下一轮模型会看到两条连续的 human,且重试时会重复计一轮
  3. 报错即销毁整个会话 —— 用户为了一个网络抖动丢掉全部上下文,惩罚过重
- **代价 / 风险**:客户端**必须**知道"重发同一条消息"这个契约,否则可能换一个 `session_id` 重发,那才会真的丢上下文。所以这条写进了 `api.py` 的模块 docstring —— 它是对外契约,不是内部实现细节
