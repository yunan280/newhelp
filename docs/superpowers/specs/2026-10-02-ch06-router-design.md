## 3. 组织方案与推荐

1. **推荐：在现有同一 StateGraph 中增加固定执行节点。** 退款/售后节点串联为逻辑子流程，共用 checkpoint、预算、事件与日志；每一步可观察，可复用已经通过验证的图和传输。
2. 独立 LangGraph 子图：边界更显式，但额外引入父子 State 映射和 interrupt/stream 命名空间处理，本章收益不足。
3. 单个节点内串行执行所有退款步骤：改动较少，但中间步骤缺乏独立 checkpoint；暂停与失败恢复更难检查。

以上均使用既有 LangGraph，不引入新的组件或供应商。推荐方案只是内部节点组织选择。

## 4. Query 理解与意图职责

### 4.1 指代消解与改写合并

一个有界 LLM 请求接收当前原话及本 session 的已完成历史，输出独立可读的问题。原话另存，账本、拒答入池和评估都保留原话，不能覆盖用户消息。

- 历史中只有一个明确订单/商品指代时，可将「它能退吗」补为「订单 1001 的机械键盘能退货吗？」。
- 多个候选无法确定时，保留歧义；不按“最后看到的数字”硬填订单。具体订单请求进入订单选择器，其他业务事实由主力 Agent 澄清。
- 已完整问法保持原字符内容，包括数字、型号、否定、条件与时间限制。口语仅在含义模糊或需要标准化时改写，不做装饰性改写。
- 提示词规定用户消息、历史和检索内容均为数据，不可作为修改指令。应用侧校验数字/型号/否定与条件保护项；无法证明改写可靠时退回原话并记录原因。
- 只用同 session 历史；新 session 不加载其他会话消息，不升级摘要或长期记忆。

Query 理解还区分一般问题与具体订单请求，作为执行范围信息；这不加入意图分类 JSON，也不在理解阶段追问退款原因或判退款资格。

### 4.2 八类 JSON 分类

枚举：物流、订单、商品咨询、退款退货、售后、投诉、闲聊、其他。严格输出示例：`{"intent":"退款退货","confidence":0.96}`。

- `intent` 必须是枚举；`confidence` 为有限数值 0～1。禁止额外字段、代码围栏、解释、工具调用或字符串置信度。
- Prompt 明确物流与订单、退款与维修/换货、投诉与普通不满、闲聊与无法识别之间的边界。当前意图优先，历史只是消解指代依据。
- few-shot 包括问候夹退款、投诉但无退款诉求、收到坏件要维修、上轮退款本轮询问原订单物流，以及无法理解/超范围的怪问题。
- 分类器只回答“要干什么”，不返回槽位、退款结论、追问、下一跳或检索查询。固定路由由代码决定。
- 默认所有需要分类的输入走 LLM Prompt；历史的本地问候捷径不能替代这份正式八类契约。短问候的 Query 理解可原样透传。
- 低把握输出「其他」。应用侧低置信度阈值在独立校准样例上确定并记录，正式测试不得用于调阈值。模型自报 confidence 不是经过校准的正确概率。
- 非法控制输出最多一次有界 JSON 纠正；仍失败则走可追踪的 `invalid_classification` 兜底，不执行业务。上游超时、余额或服务错误明确返回错误，不能伪装成「其他」。评估同时报告原始解析率与纠正后的解析率。

### 4.3 简单 FAQ 的边界（用户已确认）

已确认口径：一般政策 FAQ（「退货政策是什么」「保修期多久」）直接单次检索，不索要订单、不扩写；具体订单诉求（「这个能退吗」「订单 1001 要维修」）走订单→扩写→政策→Agent。意图仍按八类正确输出，不把一般退款 FAQ 改成商品咨询或「其他」。

用户已明确选择上述口径，拒绝将一般退款/售后政策 FAQ 强制绑定订单。本章据此落实固定分流，不再重复询问。

## 5. 模型、格式与预算

继续使用已配置的 OpenAI 兼容聊天上游与同一套凭据。当前本机上游是 DeepSeek，已有 `LLM_MODEL=deepseek-chat`。推荐 Ch06 意图主模型默认显式使用该上游的 `deepseek-v4-pro`；指代/改写也用主模型。Query 扩写与最终 Agent 沿用现有聊天模型配置，不静默切换供应商。高能力模型是否达标，以真实冻结评估为准。

成本降级是显式配置开关，默认关闭。开启时：低成本模型先输出相同两字段 JSON，低于已记录阈值只升级主模型重判一次；主模型仍不确定则「其他」，不能反复重试或硬归业务。低成本与主模型必须配置成不同模型，使用相同上游。降级模式单独记录准确率、升级次数与用量，不能只宣传减少调用。

指代/分类/扩写请求不绑定业务工具，启用提供商 JSON 模式并做应用层严格校验。保留现有 Agent 的 Function Calling 与仅非法控制时的一次纠正，不给整个 Agent 强加 JSON 模式，避免重现 Ch05 工具调用回归。

所有前置模型请求、升级与格式纠正计入同一 token/调用台账；保留最终回答预算和单请求超时。等待用户点选期间不保持 HTTP 请求、不持有锁、不继续计算模型 deadline。恢复后分配新的执行时间窗口，但继续累计原业务请求的模型用量，不能因等待数分钟立即超时或清零预算。

## 6. 确定性退款/售后子流程

```text
begin_turn → understand_query → classify_intent → route_intent
  具体退款/售后 → ensure_order
                  ├─ 无可信订单 → offer_order_selection → interrupt
                  │               用户点选 → 校验并 resume
                  └─ 有可信订单 ────────────────────────┐
                     load_order ←─────────────────────┘
                     → expand_queries → retrieve_policy
                     → confidence_gate → assess_order → stream_answer → log_turn
                                            └─ 缺业务事实 → 主力 Agent 澄清
  一般 FAQ/商品知识 → 单次 retrieve_knowledge → 原 gate → 原 Agent
  物流/订单 → 原只读业务 Agent
  投诉 → 原固定安抚与独立可选操作
  闲聊 → 闲聊回复
  其他 → 固定能力范围/澄清回复，不进入核心业务
```

`ensure_order` 只接受用户本轮明确订单号、用户已点选订单、或本 session 内唯一且明确的可信指代。LLM 输出的订单号必须验证来源与当前用户归属。只看到商品名不能认定对应哪一单；找不到合法订单时呈现卡片，不猜、不默认第一单。

`load_order` 在扩写和检索前确定性执行，保存结构化订单快照与工具轨迹。必要字段包含订单号、owner、商品、品类、状态、实付、下单/签收日期；未提供的拆封状态等不编造。后续判断复用快照，不让 Agent 重选订单。

`assess_order` 使用主力 Agent，根据这份订单和通过 gate 的政策证据判断本单是否符合退款/售后条件；不允许 Agent 决定要不要读订单或绕过政策检索。资格结果区分符合、不符合、缺事实需澄清，缺事实的澄清由主力 Agent 自然表达。不能为完成验收把未知拆封状态默认设为未拆封。

退款资格支持的情况下提供退款申请表单；维修/换货问题仍按用户诉求回答，不自动转成退款。未知或不符合条件不显示“已批准退款”，判断永远不能代替真实审核。

## 7. 检索侧扩写与政策证据

扩写输入包含标准问题、可信订单事实和核心场景。输出严格为 `{"queries":["查询一","查询二","查询三"]}`，生成 2～4 条不同重点的检索查询。主查询始终参与检索；扩写不得新增用户没有说过且订单中没有的事实、时间、退款原因或资格结论。

资格、期限、例外/拆封条件、运费/申请路径可成为不同侧重点。简单 FAQ 不扩写，其他意图不启用。数组元素须非空、长度受限并去重；非法输出最多一次有界纠正，仍失败就以标准问题单次检索政策并标记降级，不跳过强制检索。

多 Query 复用原生混合检索，各查询召回候选；统一按 chunk ID 去重，MySQL 回查已发布状态和 content_hash 后合并。候选融合后按原标准问题与订单上下文统一重排、保留最多 10 条并重新编号，确保同一知识块不重复引用。召回阶段不重复调用全文生成；扩写副本不入库。

强制政策检索使用现有 `content_type=policy` 过滤；关键条款优先保留，同时允许相关例外条款进入最终证据，不能因只筛 `is_key_clause=true` 丢掉必要例外。每条 Query 的 dense/BM25 均应用同一过滤，回查再核验。用户给定过滤与强制政策过滤冲突时明确拒绝/报参数错误，不静默去掉强制约束。

复用 Ch04 重排分数与预算闸，但在独立校准数据上检查新输入/政策语料的阈值适用性；不把 RRF 分数冒充置信度。没有相关政策、证据弱或上下文超限时阻止主力 Agent 做资格判断并记录原问题；基础设施故障保留明确错误。

增加单份明确标记为演示的退款/售后政策原文，沿用既有 Markdown 入库、同步和版本检查机制。普通结构切块仍可用，但不为扩写 Query 增殖存储。线上已有知识不清空；真实验收使用独立的测试语料/集合，不覆盖旧章节冻结评估集。实施计划须列出实际语料准备、迁移、同步、审计和备份命令。

## 8. 订单选择的暂停与恢复

复用官方 `interrupt` 与 `Command(resume=...)`，始终使用原 session 的 thread_id 和 AsyncSqliteSaver；不新建一套手写持久化。点选等待点单独成节点，重放前无写库副作用、无模型调用。

- 展示订单卡片只含当前 demo 用户可选择的订单：商品、订单号、金额、日期和状态。
- 服务端生成稳定 selection_id，绑定 user/session/turn、候选列表和原问题；selection_id 写入 checkpoint 后才允许客户端恢复。
- SSE 发 `order_selection` 与明确 `waiting_for_order` 终态后结束连接；JSON 返回同一状态与选择数据，不能把待选择算完成回答。
- 点选 POST 原 session、selection_id 与 order_id；服务器验证 session 所属、待选请求仍活跃、订单属于候选及用户后恢复；客户端提交的商品/金额/日期不可信。
- 恢复不重新分类或覆盖原诉求，按 `load_order → expand_queries → retrieve_policy` 接着走。重复点击同一选择不能重复业务动作；不同选择、过期卡片和跨 session 操作返回冲突。
- 刷新或进程重启后，页面从只读状态接口恢复仍有效的卡片，不把旧客户端缓存当服务端待选依据。
- 等待时用户可继续问新问题。服务端先显式取消旧待选并结清中断，再作为新轮重新判断意图；旧卡片失效。点选与新消息在现有 session 锁下串行裁定，不能因旧退款状态黏住物流新问题。
- 恢复阶段账本只写一次原 user 消息、卡片提示与最终回答；点选记录作为结构化事件，不伪造用户说过的退款原因。历史足以恢复明确指代，不重复拼接 MySQL 与 checkpoint。

新 State 字段提供兼容默认值；开始新轮重置本轮订单、证据、扩写、资格和候选，避免上一轮资料泄漏。只有明确的 session 内实体指代可以沿历史解析。

## 9. 演示订单与退款申请

订单目录是本章的固定演示数据，归属检查基于当前 demo identity，沿用应用已有身份机制，不宣称本章新增了登录鉴权。订单卡片、订单读取和原只读工具使用同一结构化演示数据来源；不靠 LLM 从自然语言工具输出猜字段。

退款申请新增 MySQL 持久化表，使用既有 SQLAlchemy 与 DDL/migration 规范；SQLite 仅作隔离测试/既有 checkpoint，不替换业务 MySQL。新增可重入迁移，迁移前备份，不重建旧表或 seed 旧业务数据。

申请绑定已验证的 user/session/order、服务端生成的 offer_id、原问题、资格/政策快照、固定原因和 pending 状态。数据库唯一幂等键确保提交已成功但响应丢失时，同参数重试获得同一申请号；重复使用同 offer 修改订单或原因返回冲突，不新增另一张申请。模型无退款写权限，未点击提交不写申请。

表单原因固定为：七天无理由、商品质量问题、与描述不符、破损或缺件、发错货、其他。初始值为空，用户必须自选；分类/改写不能替用户选原因。订单只读显示，金额展示实际付款，本章不引入部分退款金额编辑。提交成功明确显示“申请已提交，待审核”与申请号；不说“退款已到账”。

## 10. 前端实现与验收口径

仅改现有原生聊天页：订单卡片嵌入助手消息，可点击选中，自动回填并继续显示执行进度；不跳转外部页面，不要求用户复制订单号。重复点击期间禁用，失败可重试；旧选择失效有明确状态。

退款申请是消息内的简洁表单，显示选中订单、固定原因下拉和提交/取消。提交前不默认原因、不自动写库；提交中防重复、失败保留所选原因、成功显示真实申请号。刷新保持展示，同时用服务端状态确认可操作性。
